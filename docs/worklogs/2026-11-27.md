### 작업·검증 조건

- 브랜치: `sec/sec-001-server-hardening`(기준 `main` `faa060e`, PR #13 병합 뒤)
- 환경: WSL2 Linux, Node 24.22.0, socket.io 4.8.4, zod 4.6.7, Playwright 1.64.1 Chromium 헤드리스(SwiftShader WebGL)
- DB: 로컬에 Docker·PostgreSQL이 없어 사용자 허용 뒤 scratchpad에 `embedded-postgres`(PostgreSQL 17.5 바이너리)를 받아 `initdb`·`pg_ctl`로 TCP 54329에서 띄웠다(유닉스 소켓 경로가 107바이트를 넘어 `unix_socket_directories=''`). 프로젝트 의존성에는 넣지 않았다. 확인 뒤 서버를 멈췄다.
- 브라우저 확인용 서버: ① DB 없이 `createAppServer`(연결 안 되는 풀)로 `packages/client/dist`를 제공 — 로그인·로컬 2인·AI 대전 ② 실제 `packages/server/src/index.ts`(마이그레이션 포함)를 로컬 DB로 실행 — 두 계정 로비·대기실·온라인 경기. 둘 다 `NODE_ENV` 미설정(개발 설정)이라 HSTS는 단위 테스트로만 봤다. 세션 비밀값은 실행마다 `openssl rand`로 만든 임시 값이며 기록하지 않았다.

### 수행과 관찰

변경:

- `security/headers.ts`: 모든 응답에 CSP(`'self'`만, `object-src 'none'`·`base-uri 'none'`·`frame-ancestors 'none'`)·`X-Content-Type-Options: nosniff`·`Referrer-Policy: same-origin`, 운영에서만 HSTS(`max-age=31536000`). `/health`보다 앞에 둔다.
- `realtime/origin.ts`·`socket.ts`: `allowRequest`로 `Origin`의 호스트가 `Host`와 다르면 핸드셰이크 403. `maxHttpBufferSize` 4 KiB.
- `game/game-rate-limit.ts`·`game-handlers.ts`: 사용자별 1초 고정 창. 경기 명령 묶음 10, `board:rotate`·`aim:update`·`hazard:aim` 각 30. 명령은 ack `RATE_LIMITED`, 스트림은 버린다. 한도를 넘긴 첫 호출에 서버 로그 `rate_limited` 한 줄. `room:join` 제한기와 고정 창 구현(`realtime/fixed-window.ts`)을 함께 쓴다. `shared`의 게임 오류 코드에 `RATE_LIMITED`, 클라이언트 안내 문구를 더했다.
- `config.ts`·`app.ts`: `SESSION_SECRET_PREVIOUS`가 있으면 `express-session`의 `secret`을 `[현재, 이전]`으로 둔다(서명은 현재 값, 검증은 둘 다). `.env.example`에 항목을 더했다.
- `shared/no-jit.ts`: 아래 CSP 위반을 없애려고 더했다. 브라우저 진입점 3곳이 첫 import로 불러 Zod JIT를 끈다.

근거로 잰 값:

- 클라이언트 → 서버 최대 정상 메시지(스키마 통과, 숫자 17자리·음수, 모든 선택 필드): `aim:update` 359바이트, `hazard:use` 298, `hazard:aim` 235, `room:create`(이모지 제목 10자) 163. 상한 4 KiB는 최대치의 약 11배이며 테스트가 1/4 아래를 고정한다.

### 한계·미검증

- HSTS는 HTTPS 운영 환경에서 브라우저로 보지 않았다(단위 테스트만). [OPS-004](../TASKS.md#ops-004-운영-서버-구축)에서 실제 도메인으로 확인한다.
- 한도는 클라이언트 코드의 최대 빈도와 자동 연속 입력으로 정했다. 사람 두 명의 실제 경기 빈도는 재지 않았다. 운영의 `rate_limited` 로그로 정상 사용자가 걸리는지 본다.
- 브라우저는 헤드리스 Chromium만 확인했다. `connect-src 'self'`가 `ws:`를 포함하는 동작은 CSP Level 3 브라우저(현행 Chrome·Firefox·Safari) 기준이다.
- 프록시 뒤(Caddy·Cloudflare)에서 `Host`가 유지되는지는 OPS-004 구성에서 확인한다.

### 문서 대조·후속 작업

- AUTH·API·OPERATIONS를 같은 변경에서 갱신했다. AUTH의 `trust proxy` 설명(Render 1단)은 그대로이며 [OPS-003](../TASKS.md#ops-003-배포-자동화)에서 바꾼다.

## OPS-005 DB 백업·복구

### 범위와 기준 문서

- 작업: [OPS-005](../TASKS.md#ops-005-db-백업복구)
- 설계: [OPERATIONS 백업·복구](../design/OPERATIONS.md#백업복구), [DEC-096](../DECISIONS.md#결정-색인)·[DEC-098](../DECISIONS.md#결정-색인)·[DEC-099](../DECISIONS.md#결정-색인)(알림 채널 Discord)
- 이번 범위: 사용자가 OPS-004 병합 뒤 "3번 진행하자"(OPS-005)를 요청했다. 사용자는 Slack·다른 채널을 물은 뒤 Discord 웹후크를 만들었고, R2 버킷·API 토큰·웹후크를 직접 VM 환경 파일에 넣었으며 백업 암호를 VM 밖에 보관했다. 도구(pgBackRest)·주기·보관 개수·알림 방식은 Claude가 승인된 방향 안에서 정했다.

### 작업·검증 조건

- 브랜치: `ops/ops-005-db-backup`(기준 `main` `fb526fd`). VM은 이 브랜치를 받아 실행했다.
- VM: HostHatch 서울(OPS-004), PostgreSQL 17 + pgBackRest 2.60.1, R2 버킷 `alkkagi-backup`(이 버킷만 객체 읽기·쓰기인 토큰). 비밀값은 `/opt/alkkagi/.env`(600)에만 있고 Claude는 값이 채워졌는지만 봤다.

### 수행과 관찰

- `deploy/postgres/Dockerfile`(PGDG의 pgbackrest), `pgbackrest.conf`(R2·암호화·zstd·전체 4개 보관), Compose의 `PGBACKREST_REPO1_*` 환경, `backup.sh`·`backup-check.sh`·`backup-lib.sh`·`backup-setup.sh`·`restore-drill.sh`, systemd 서비스·타이머를 만들었다.
- `backup-setup.sh` 종료 코드 0: stanza 생성 2.2초, `check`에서 첫 WAL 조각 보관 성공, 첫 전체 백업, 타이머 3개 설치(다음 차등: 토 04:00 서울, 전체: 일 04:00 서울, 확인: 10분마다). 설정 완료 Discord 알림 전송.
- 첫 전체 백업이 375초 걸렸다(DB 30 MB, 저장 3.6 MiB). 작은 파일 약 1,290개를 하나씩 올린 탓으로 보고 `repo1-bundle=y`를 켠 뒤 다시 전체 백업: 12초, 3.6 MiB.
- WAL 보관 간격: 운영 경로(Cloudflare)로 연습 계정 2개를 가입한 쓰기(08:00:57 UTC) 뒤 35초에 보관, 삭제 쓰기(08:01:46) 뒤 46초에 보관. `archive_timeout=60s`와 맞다.
- 시점 복구 연습(`restore-drill.sh`, 임시 컨테이너): 삭제 전 시점 `2026-11-27 08:01:37+00`으로 복구하면 회원 2명(운영 0명), 최신 시점으로 복구하면 0명(운영과 같음). 복구 소요 9초·8초(파일 1,286개, 29.9 MB). 끝난 뒤 임시 컨테이너·볼륨이 남지 않았다. 연습 계정은 운영에서 지웠다.
- 알림 시험:
  - 백업 실패: `systemctl start alkkagi-backup@bogus.service` → 실패 종료, Discord "DB 백업 실패(bogus): … 'bogus' is not allowed for 'type' option".
  - WAL 보관 실패: `archive_command='false'`로 바꾸고 `pg_logical_emit_message` + `pg_switch_wal()` → `backup-check.sh`가 "WAL 보관 실패 중" 알림(종료 1), 바로 다시 실행하면 알림 없음(중복 방지). 원래 명령으로 되돌리자 밀린 조각이 보관되고 "WAL 보관 복구됨" 알림.
- 실수와 정정:
  - 첫 실패 시험에서 쓰기 없이 `pg_switch_wal()`만 해 전환이 일어나지 않아 실패를 만들지 못했다.
  - 되돌릴 때 `ALTER SYSTEM RESET archive_command`를 써서 명령이 빈 값이 됐다(보관이 멈추고 WAL이 VM에 쌓이는 상태). 약 2분 뒤 원래 명령을 다시 넣고 `check`로 보관을 확인했다. R2의 WAL은 `…01`~`…0F`까지 빈 구간이 없다. OPERATIONS에 주의 문구를 넣었다.
  - WAL 평균 크기(164 KiB)를 보고 재활용 때문이라 판단해 `wal_recycle=off`를 켰으나, 실제로는 첫 조각(2 MB)만 크고 나머지는 약 0.7 KB였다. 근거가 틀려 `ALTER SYSTEM RESET wal_recycle`로 기본값(on)으로 되돌렸다.
- R2 사용량: 객체 1,313개, 10.01 MiB(대부분 묶음 전 첫 전체 백업의 파일). 최종 `postgresql.auto.conf`는 `archive_mode='on'`, `archive_timeout='60s'`, `archive_command='pgbackrest --stanza=alkkagi archive-push %p'`뿐이다.
- 디스크 62%(5.5 GB/8.9 GB).

수용 기준 판정: 4개 모두 충족(보관·주기 백업·도구·보관 개수·사용량 기록, 실패 알림 시험, 시점 복구·소요 시간·손실 범위, 월 1회 복구 연습 절차).
