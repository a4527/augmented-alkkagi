# 1인 개발 작업 규칙

2026-11-25부터 개인 프로젝트로 진행한다([DEC-091](DECISIONS.md#결정-색인)). 전환 전 두 개발자의 담당·리뷰 기록은 [TASKS](TASKS.md)·팀 저장소 Issue·PR에 그대로 남긴다.

## 기본 흐름

TASKS의 작업 선택·등록 → 관련 기준 문서 확인 → 작업 브랜치에서 수정·검증 → worklog 기록 → PR → 자기 검토 → 기준 브랜치 병합 → TASKS 완료 반영.

- 작업 ID·우선순위·의존성·상태·수용 기준은 [TASKS](TASKS.md) 한 곳에서 관리한다. Issue는 필요할 때 작업 메모·외부 연결에 쓰고 TASKS의 해당 작업을 연결한다.
- 작업별 문서 선택은 [AGENTS](../AGENTS.md)를 따른다. AI와 함께 작업할 때도 작업 중인 변경을 덮어쓰지 않는다.
- 기준 브랜치는 [PROGRESS](PROGRESS.md)에 명시한다. 작은 문서 수정도 작업 브랜치에서 하고 PR로 병합해 변경 근거를 남긴다.
- [PR 양식](templates/PULL_REQUEST.md)에 작업 ID, 변경 내용, worklog의 검증 근거, 기준 문서 갱신을 연결한다.
- 작업을 마무리하는 PR은 병합 전에 TASKS의 수용 기준을 모두 충족하고 체크해야 한다. 단, "자기 검토 후 기준 브랜치에 병합됐다" 기준은 병합으로 충족되므로 병합 직후 체크한다. 수용 기준이 남은 중간 PR은 남은 기준을 PR 본문에 적는다.
- 수용 기준이 충족돼도 자기 검토·기준 브랜치 병합 전에는 작업을 완료로 표시하지 않는다.
- 이슈의 작업을 마무리하는 PR은 본문에 `Closes #이슈번호`를 적어 병합 시 이슈가 자동으로 닫히게 한다. 마무리하지 않는 PR은 이슈 번호만 연결한다.

Issue·PR 본문 양식은 `docs/templates/`에서 복사해 사용한다. GitHub 자동 인식 경로가 아니므로 자동 적용되지 않는다.

## 자기 검토

상대방 리뷰를 대신해 병합 전에 PR의 전체 변경(diff)을 다시 읽고 다음을 확인한다.

- TASKS 수용 기준을 하나씩 대조하고, 확인된 항목만 체크했다.
- 관련 PRD·설계·결정과 어긋나는 동작이나 문서 중복이 없다. 요구사항·설계·결정이 바뀌었으면 해당 기준 문서를 같은 PR에서 갱신했다.
- 변경에 맞는 실제 명령(`npm test`·`npm run lint`·`npm run format` 등)과 관련 시나리오로 검증했고, 결과·한계를 worklog에 남겼다.
- 비밀정보·환경변수 값이 변경·문서·로그에 없다. 비밀값 검사(gitleaks)에서 테스트 전용 값이 오탐되면 값과 위치를 확인한 뒤 [.gitleaksignore](../.gitleaksignore)에 지문과 근거를 등록하고, 실제 비밀값이면 등록하지 않고 폐기·교체한다.
- AI 도구가 작성·검토한 변경도 같은 기준으로 직접 확인한다.

## 결정 기록

- 작은 결정은 [DECISIONS](DECISIONS.md), 중요한 선택은 ADR에 기록한다. 동의 근거와 대체 관계를 남기며 미정·후보를 승인으로 간주하지 않는다.
- 외부 서비스·API 계약을 바꿀 때는 관련 문서와 코드를 함께 갱신한다.

## 검증·기록

- 검증 결과는 [worklog 양식](worklogs/TEMPLATE.md)에 따라 같은 날짜 파일에 작업 ID별로 추가하고 TASKS·PR에서 해당 절을 연결한다.
- 검증 방법·트러블슈팅·변경 이력의 작성 위치는 [AGENTS](../AGENTS.md#작업-목적에-따라-읽을-문서)를 따른다.
